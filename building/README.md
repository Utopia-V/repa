# 一起建设 Repa

Repa 想在真实而漫长的学习过程中承担 Tutor 的责任。学习者带着课程、材料、问题、目标、作业和有限的时间来到这里；Repa 需要理解眼前的处境，选择合适的教学或学习动作，并在后续互动中根据新的反馈重新判断。

我们关心的结果很朴素：原本难懂的内容逐渐能够学下去，学到的东西以后还能想得起、理解得更深、用得上。一次好的解释、一个恰当的例子、一段独立完成的工作和一次及时的回顾，都可能推动这个结果。

稳定产品判断的规范版本集中在 [Product constitution](../docs/foundation/00-product-origin.md#product-constitution)。`building/` 用具体情境、模型观察和当前代码经验展开这些判断，不另建一套竞争性的产品权威。

## Tutor 在哪里

Tutor 是整个 Learning System 表现出来的行为。模型、程序和学习者在其中承担不同的工作。

学习者提出目标，提供材料和真实处境，完成理解、回忆、推理、练习、创作和应用，也随时可以改变当前方向。模型擅长理解开放语言和材料，能够解释、演示、比较、出题、研究、规划并根据对话作出局部判断。程序让这段学习关系跨越时间：它保存可靠的身份和来源，执行有约束的修改，处理权限、事务、失败和恢复，并为模型准备当前真正用得上的背景。

三者共同形成一个循环：

```text
当前的学习处境
      ↓
选择下一步教学或学习动作
      ↓
解释、演示、探索、练习、回顾或完成真实工作
      ↓
观察问题、回答、作品和结果
      ↓
更新对处境的理解，再选择下一步
```

这个循环可以从任何地方开始。学习者可能想先看整体，也可能正在卡住一道题；可能需要一个例子，也可能已经准备独立完成任务。Repa 要在自然对话中接住这些变化，学习者无需先整理一套内部状态。

## 当前系统是一份工作答案

Repa 已经有一条完整的本地 Agent 运行主干，也已经实现课程与材料、长期目标、未来关注点、作业、学习判断和学习建议等能力。每次模型采样前，系统会准备有限的学习背景；模型还能按需读取细节，并通过明确的工具发起真实修改。

对今天的运行、维护和故障分析而言，这些代码、类型和测试是真实的生产事实。对后续重构而言，它们主要是行为与问题的证据，不是下一版架构的默认模板：一个实体已经存在、一套 revision 或 settlement 已经实现、一个旧测试能够通过，都不单独证明同样的边界应当继续存在。简写为：**当前系统是 behavior oracle，不是 architecture oracle。** 这句话不否认当前 runtime；它限制的是从当前形状推导未来形状的方式。

这些实现让许多过去停留在概念层的问题变得可以运行、观察和修正。其中已经显现的难题包括：模型怎样在长对话和多次工具调用中保持学习主线，怎样利用通用大模型已经习得的行为形状，怎样安排跨时间的学习和复习，以及长期学习信息究竟应该怎样表达和保存。

我们会继续用真实学习、模型实验和工程证据检验当前方案。模块完成以后，我们才有机会在实际使用中看到它带来的行为；这些观察会继续改变产品判断。

## 这套材料怎样变化

稳定产品含义发生变化时，先更新 product foundation，再让本页和学习情境跟随。模型、时间和数据章节保存正在形成的理解，也记录足以改变后续研究方向的观察。新的核心问题若在多个学习情境中反复出现，并且需要持续研究，可以在 `building/` 中形成自己的章节。代码变化由“当前的 Repa”和开发章节跟进，Git 负责保存具体版本和时间。

共同建设 Repa 的人可以挑战当前方案。一个新的解释应当回到学习者的处境，说明它会怎样改变 Tutor 的行为，并指出我们可以从哪里观察到这种改变。
