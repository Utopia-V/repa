# Repa Issues 产品目的与路线研究

## 研究范围与方法

研究时间：2026-09-01。

本记录以仓库当前公开的 GitHub Issues、仓库内产品文档、ADR、README、当前实现和测试为一手来源。研究入口是 [Utopia-V/repa Issues](https://github.com/Utopia-V/repa/issues)。入口页当前显示 6 个开放 Issue（#3–#8）：#3、#5、#6、#7、#8 使用 `question` 标签，#4 使用 `ready-for-agent` 标签。Issue 之间没有已登记的 assignee、project 或 pull request 关系；正文中的 Parent 关系如下：#4 属于 #3，#6/#7/#8 属于 #5。

仓库自己的词汇和边界以 [`CONTEXT.md`](../../CONTEXT.md) 为准；当前交付状态以 [`README.md`](../../README.md)、当前源码和测试为准。以下内容中：

- **事实**：Issue、文档或代码明确写出的内容。
- **推断**：由多个事实合并得到的产品判断，不把它当作已经验证的用户研究结论。

## 结论摘要

### 产品目的

Repa 的目的不是做一个固定课程、自动排课器或会给学习者打分的 AI 老师，而是做一个**本地优先、可长期协作的通用学习 Agent**：学习者像使用普通 Agent 一样直接提问；当当前请求需要时，Agent 再调用学习计划、来源材料、学习 Wiki、历史和学习证据等能力，帮助学习者解释、检索、整理、回顾和重新安排学习。

它要解决的核心问题是：普通 Agent 擅长回答眼前问题，却容易忘记多个并行目标、期限、现实限制和不断加入的材料；即使这些信息存在外部文件中，学习者也不确定 Agent 是否读取了最新版本。[#3 的问题陈述](https://github.com/Utopia-V/repa/issues/3) 和当前设计入口 [#5](https://github.com/Utopia-V/repa/issues/5) 都明确把这个问题作为 Repa 的出发点。

### 产品的四个核心原则

1. **当前请求优先，长期能力按需介入。** 普通对话不必产生长期写入；只有当前请求需要时，才整理笔记、更新计划、回顾进展或加载历史。[#5](https://github.com/Utopia-V/repa/issues/5)
2. **当前状态必须压过旧对话。** 目标、期限和可用时间会变化；Agent 不能被旧 Session 中已经过期的说法牵着走。[#6](https://github.com/Utopia-V/repa/issues/6)
3. **学习资料和结果由学习者拥有。** 学习数据保存在学习者自己的本地空间；远程模型可以使用，但只发送当前调用选择的上下文。Wiki 正文等长期工件应可直接查看、修改和核验。[`CONTEXT.md`](../../CONTEXT.md)、[#3](https://github.com/Utopia-V/repa/issues/3)
4. **Agent 辅助判断，但不夺走学习者控制权。** Agent 可以给建议、生成练习、评价回答和指出计划偏离；学习者仍拥有最终的掌握判断，也可以忽略建议。[#3](https://github.com/Utopia-V/repa/issues/3)

### 目标用户

**核心用户是有持续学习目标、会积累自己的材料、且现实约束会变化的自驱型学习者。** 典型情境包括同时准备多个考试、学习工作技能、维护一组长期兴趣，或者已经有 Markdown 笔记/个人知识库但希望有人帮助整理和重新安排。这里的“学习者”不要求是正式学生，也不要求预先选择课程。[`CONTEXT.md`](../../CONTEXT.md)、[#5](https://github.com/Utopia-V/repa/issues/5)

用户真正需要的不是更多一次性答案，而是：

- Agent 记得当前真正有效的目标和限制；
- 能从自己的文件和来源中找回依据；
- 在多个目标之间重新平衡投入；
- 允许 Agent 整理，但每次持久改动都可见、可修正、可恢复；
- 长期积累最终变成自己拥有的知识网络，而不是锁在服务商里的聊天记录。

**早期采用者画像是推断，不是已完成的用户研究结论。** 由于当前产品要求用户指定本地目录、配置 Pi provider，并通过最小 TUI 使用，第一批更可能是愿意管理本地文件、接受命令行和自行配置模型的学习者。长期目标则明显比这个早期画像更宽：文档没有把正式学生或技术背景设为前提。

### 当前产品状态

当前仓库已经完成第一条可运行细线：打开学习者空间、通过 Pi provider 流式对话、取消生成、正常关闭并恢复 Session、显式信任后加载兼容的 Package/Extension/skill/prompt，并通过统一的 Repa Application command/event interface 供 TUI 和测试使用。[`README.md`](../../README.md)、[#4](https://github.com/Utopia-V/repa/issues/4)、[实现提交 540b9c9](https://github.com/Utopia-V/repa/commit/540b9c923fa7fe043fde51e249d0a7b8ccf1ad43)

但这不等于完整产品已经交付。README 明确说明：学习计划、学习者记忆、学习 Wiki、来源材料和历史搜索还没有进入生产实现。当前测试证明的是 Agent runtime、工具闭环、Session/compaction 和错误处理等工程行为，不证明真实 Model 已经能持续改善学习结果。

## 如何达到产品目的

### 1. 先把产品承诺收窄成一个可验证闭环

建议把第一阶段承诺写成：

> 学习者可以像和普通 Agent 聊天一样提出任何学习请求；当请求涉及长期目标时，Repa 使用最新状态和相关材料，给出可解释的帮助，并且所有持久修改都由学习者拥有、可见和可恢复。

这个承诺同时覆盖 #5 的自然交互、#6 的状态可靠性、#8 的计划质量和本地优先原则；也明确排除固定课程流程、强制 scheduler、自动掌握评分和后台自动化。

### 2. 先解决“最新状态”而不是先堆知识图谱

围绕 #6 建立最小的当前状态语义：目标、期限、当前限制和状态变化都要有明确版本。每次 Model 调用始终注入小而稳定的当前目标轮廓；详细计划、来源和历史只在请求相关时按需读取。旧 Session 仍保留为“过去发生了什么”，但不能成为当前目标的权威。

验收至少包括：

- 期限延期后，“今天该学什么”不再按旧期限回答；
- 可用时间从三小时变成九十分钟后，计划不再使用旧容量；
- compaction、关闭重启后仍使用最新状态；
- 发生并发修改时，不静默覆盖学习者的新状态；
- 普通概念问答不加载完整计划，也不产生计划写入。

### 3. 用“Agent 负责理解，程序负责约束”落地规划

按 #8 的边界，把职责拆成两层：

- Agent 理解学习者意图、多个目标之间的优先级、缺失信息和说明文字；
- 规划程序读取权威状态、检查时间/期限/重复分配/遗漏目标/最低投入/版本，并在失败时返回具体可修正原因。

计划先区分“只给一次建议”和“学习者要求保存”。保存采用期望版本检查；冲突时拒绝覆盖，重新读取并让 Agent 重排。通过固定场景比较“直接规划”和“有规划程序”，只保留能带来可观察改善的机制。这样可以得到 #8 要求的产品证据，而不是凭感觉增加一个复杂的规划框架。

### 4. 让长期数据成为学习者的资产，而不是 Agent 的黑箱记忆

实现长期能力时坚持以下边界：

- 学习 Wiki 正文继续放在学习者可直接打开和修改的普通文件中；索引和元数据可重建；
- 来源材料与实际 Session 历史保持不同含义，回答中的模型知识不能伪装成引用；
- 每次 Agent 写入都返回简短变化说明、版本或冲突信息；
- 直接界面操作和 Agent 工具调用使用同一领域行为；
- 任何派生索引损坏都能从原始文件/Session 重建。

这些边界来自 [`CONTEXT.md`](../../CONTEXT.md) 和 [ADR-0003](../adr/0003-share-file-based-content-operations.md)。它们会直接支撑 #7 的可视化：Wiki 树应该是学习者已有资产的可探索视图，而不是另一份会和文件正文竞争的数据库。

### 5. 用同一 Application seam 扩展到 GUI

当前 #4 已经建立了 TUI、测试和 Pi host 之间的 Application command/event seam。后续计划、来源、Wiki、历史和冲突事件都应继续加入这一层；TUI、GUI 和测试都作为 Adapter 使用它。这样视觉 Wiki 可以先用本地 browser demo 验证，但不会把产品语义绑死在某个前端。

### 6. 用可观察证据而非功能数量判断进展

建议按以下四类指标验收：

1. **状态正确性**：目标/期限/可用时间改变后，Agent 使用新版本的比例和错误案例。
2. **规划增益**：相对于直接规划，遗漏目标、时间冲突、过期版本写入和返工是否减少。
3. **学习者控制权**：普通对话无意外持久写入；每次写入可见；冲突不丢数据；原始文件可脱离 Repa 使用。
4. **长期使用价值**：学习者是否愿意回到本地 Wiki/知识视图，并能理解内容如何从日常学习中累积。

前两类应先用确定性测试保证行为，再用授权的真实 Model 做小规模人工评价；当前仓库已有测试明确避免凭据、网络和付费调用，因此不能把脚本化 provider 的通过误读成真实学习质量已经证明。

## 主要风险与待决策事项

### #3 与 #5 的规格冲突

#3 的后半部分非常完整，但正文已经明确说它正在重讨论；#5 才是当前设计入口。若直接照着 #3 建 SQLite、记忆、证据和工作集，容易把上一版候选设计误当作已确认需求。应在 #6/#8 得到证据后只保留被验证的部分，并为 #7 的视觉需求补上新的、前后一致的数据边界。

### 价值面过宽

当前同时出现普通 Agent、最新状态、学习计划、Wiki、来源、历史、学习证据、可视化知识树和 Pi 生态兼容。它们都合理，但不能同时作为第一阶段完成条件。最小顺序应是：普通对话 → 当前状态可信 → 规划可靠 → 可编辑长期资产 → 视觉化积累。

### 本地优先不等于完全离线

仓库定义允许 v0 使用远程 Model；本地优先指持久学习数据由学习者拥有，不指模型一定在设备端运行。产品文案、权限提示和隐私预期必须保持这个区分。

### 当前工程通过不等于模型行为通过

#4 的测试可以证明工具调用、Session 恢复、compaction、错误事件和信任边界；#6/#8 还需要观察真实 Model 是否真正选用最新状态、能否根据校验错误重排计划、是否少遗漏目标。这是产品验证，不应只用 TypeScript 测试覆盖率替代。

## 推荐的下一步

1. 用 #5 作为当前产品语义入口，写一份短的新规格草案；明确核心承诺和不做事项。
2. 完成并记录 #6：当前目标/限制的最小状态模型、注入方式、版本语义和场景证据。
3. 基于 #6 的状态语义实施 #8 实验；先验证规划程序是否带来可观察改善，再决定是否正式产品化。
4. 对 #7 做低成本本地 browser prototype；只验证视觉吸引力、导航和“知识在生长”的感觉，不提前确定长期图模型。
5. 回到 #3，删除或改写未被验证的旧候选设计，形成一份新的、可拆分的规格。
6. 最后再把稳定的学习计划、来源、Wiki、历史和 GUI 能力按同一 Application seam 逐步实现。
