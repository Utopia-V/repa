## Decision summary

Gate 22 proposes the following learner-visible composition:

```text
ordinary natural-language inspect request in the primary TUI
+ one registered owner-native current/exact/history read
+ owner-reference-first Interaction/deletion/admin consumer reads in the same
  database cut, validating every applicable coverage/integrity seal
+ explicit separate cuts and revalidation for another owner or later page
-> one typed, non-mutating pre-settlement inspection result visible in the TUI
   beside any model-authored explanation
+ a separately typed post-settlement Interaction delta for this inspection
  only after its Tool/Assistant/Turn facts actually settle

natural learner correction
-> the existing owning command, permission, and settlement path
-> immutable owner successor or truthful no-effect/failure
-> a fresh owner-specific resolution and inspection without rewriting the old
   action or automatically resubmitting a stale correction
```

The inspection result distinguishes:

1. durable owner truth;
2. exact operational lineage;
3. the strictly allowlisted body-free lineage retained by the learner-selected
   deletion mode; and
4. unavailable, partial, absent, pending, failed, or unknown truth.

Every section identifies the exact observation cut and coverage from which it
was derived. Section results from different cuts are never silently presented
as one atomic database moment. Mutable relations are revalidated before
composition; a failed revalidation produces typed stale or partial truth. The
inspection Tool cannot observe its own not-yet-settled result, later Assistant,
or terminal Turn. Those facts can appear only in the separate post-settlement
delta or a later inspection.

Gate 22 adds no universal consumption, action, purpose, activity, adherence,
mastery, causal-attribution, or audit owner. It does not require a GUI, a full-
screen dashboard, a second interpreter, a second runtime, or a dedicated
command language. The ordinary Agent may resolve a learner's natural reference
through bounded reads; the learner does not routinely coordinate internal IDs
or records.

Decision ID `G22-INSPECT-001`.

## Parent learning outcome

The learner must be able to ask, in the same natural-language TUI used for
learning:

- what Repa currently records about a Course, Goal, obligation, difficulty,
  suggestion, future concern, source, or earlier interaction;
- who reported, observed, inferred, or authored it and from which exact source;
- whether the inspected revision is current, superseded, stale, missing, or
  source-unavailable;
- which owner-native consumers or control constraints it is eligible to affect,
  without claiming that any eligible consumer actually used it;
- where that exact revision entered retained operational lineage, if that fact
  remains knowable;
- whether an exact structured current-purpose binding, completed learner-visible
  Gate 21A action result, or owner-specific finalization actually exists;
- the explicit limit that this lineage cannot explain why the Tutor produced a
  particular answer; and
- how to correct the owning meaning without editing a derived view.

The answer must not depend on the learner knowing an entity ID, revision number,
Assistant message ID, Context fingerprint, or tool name before asking. Exact
identities remain visible when they are needed to distinguish history or bind a
correction, but they are not the interaction language the learner must invent.

This Gate is not a routine audit after every explanation. Inspection is an
ordinary available Tutor action used when the learner asks, when a correction
needs an exact target, or when truthful resolution of a disputed record or
action requires it.

Decision ID `G22-OUTCOME-001`.

## Truth model

### Durable owner truth

Each domain owner continues to define its own identity, complete revision,
source, authorship, epistemic status, current/history relation, lifecycle,
staleness, and correction semantics. Gate 22 may compose those reads but cannot
normalize distinct meanings into one generic state row.

At minimum, the inspection projection preserves the distinctions relevant to
the selected owner, including:

- report, observation, model/learner-authored inference, advice, obligation,
  policy, and interaction evidence where those categories exist;
- exact revision and that owner's actual current, selected-working,
  alternative, active, open, completed, retracted, superseded, expired, or
  immutable relation where defined; there is no generic `current head`;
- immutable command/admission basis versus current read-time source status;
- explicit uncertainty, assumptions, and limits rather than inferred
  confidence; and
- owner-specific lifecycle, potential consumer/control scope, and correction or
  supersession route without borrowing completion, selection, or success
  meaning from another owner.

Assignment completion is not learning. A learner-state judgment is not mastery.
An advisory suggestion is not a commitment or selected plan. Time, silence, and
absence establish no activity, progress, adherence, breach, abandonment, or
acceptance.

### Exact operational lineage

Operational lineage is mechanically observable only to the degree retained
owner and Interaction evidence supports it. For one exact owner revision and
one explicitly bounded search range, an inspection may truthfully report:

- semantic/full or locator-only presence in an immutable Context cut;
- absence of that exact revision from the cut together with the section's
  aggregate coverage state, such as complete, truncated, withheld, stale, or
  unsupported; aggregate omission metadata does not identify which absent
  revision was omitted;
- a terminal, catalog-registered owner-native lazy-read Tool result that
  returned the exact revision;
- a first-applied typed owner citation that names the exact revision as authored
  basis or reference under that owner's semantics;
- the admitted model operation and its sealed `completed | failed |
  interrupted` status;
- the exact structured conditional-current-purpose binding that program-owned
  composition placed over the operation, including owner/candidate/source/
  target revisions, source reason, priority, scope, and control interval;
- the actual learner-visible Gate 21A Assistant/tool/terminal-Turn action result
  in the enclosing exact Interaction chain, which may require a later model
  operation, or its typed absence; and
- an owner-specific finalization fact when that owner has one, including the
  FutureAttention `served | not_served` receipt, without collapsing physical
  invocation, semantic effect/replay, operation completion, and owner
  finalization into one event.

The FutureAttention conditional-default binding is positive only when the
immutable cut records complete coverage, `countAtCut === 1`, one semantic/full
entry, its exact source/currentness tuple, and the bounded control interval.
Several entries or locator-only/partial coverage does not create a singular
binding or priority winner. An incompatible exact learner request does not erase
an otherwise valid sole binding: the cut still records that conditional
current-purpose contribution, while the exact request has higher priority for
the overlapping present action. The concern's open/finalized lifecycle remains
separate. Retained steering controls its own non-overlapping scope, and audit/
storage order is never priority.

For a command/finalization chain, the projection preserves the command owner's
causal occurrence/effect address, the physical invocation `PartID` and bound
Assistant/model-operation identity, the immutable physical result, the semantic
effect/change-set identity, and the later claim/finalization receipt identity.
Exact physical replay always returns the original admission-cut result byte for
byte. If that result said FutureAttention finalization was pending, a later
`served | not_served` receipt is shown as a separate current owner fact; Gate 22
never refreshes or rewrites the old Tool result. A physically new same-address
semantic duplicate may expose a current owner projection only under that
command's existing replay/duplicate rules.

These statements bind exact LearnerHome/database identity, owner identity and
revision, Session, Turn, Input/occurrence, Assistant message/model operation,
Context cut/fingerprint, Tool Part, Assistant content, and terminal Turn state
where each identity is available. A historical query never substitutes the
owner's later current or working relation for the exact revision bound to the
old operation. The current-purpose binding is operation-bound and the Gate 21A
action result is bound to the exact Interaction chain. They do not create a
generic per-record `selected` or
`caused answer` relation.

The search boundary is part of the result. “No matching lineage in these exact
retained Sessions/Turns/pages” is not “never used.” A stale cursor, page limit,
query failure, unavailable Session, deleted source, or unsupported owner arm
must remain explicit rather than becoming an empty result.

### Observation cuts and current-inspection settlement

One visible inspection may compose several producer reads, but it is not
allowed to pretend that separate Tool calls observed one indivisible moment.
Within one supported owner inspection action, the owner and consumer projections
share one outer SQLite transaction/snapshot. Additional owner Tools or later
pages have their own cuts. The visible composition carries:

1. each owner-native Tool result carries its database/LearnerHome identity,
   exact query target, owner-defined current/history relation, requesting Tool
   candidate/Part identity and schema version, stable ordering boundary,
   page/byte/work coverage, and continuation cursor where applicable; that
   Part's later terminal settlement is explicitly outside the cut;
2. one Interaction-lineage page executes its dependent joins inside one SQLite
   read snapshot and records the exact finite Session/Turn/operation scope it
   actually examined, catalog/projector versions, deletion-audit or
   administrative-history seal identities, terminal/coverage state, and page/
   work coverage;
3. `complete_negative` is legal only when that one snapshot processes the whole
   declared finite scope within the work bound and every included model
   operation has terminal candidate coverage plus a valid operation seal. An
   admitting, running, terminalizing, unsealed, over-budget, or otherwise
   unexamined operation creates `pending_interaction_gap`, `unsealed_gap`, or
   `scope_over_budget`, never a negative;
4. before composing a current or selected-working owner relation with the
   lineage section, the reader revalidates that relation and every mutable
   seal/purge/finalization identity used by the result. A mismatch returns
   `stale_inspection`; an unavailable dependent section returns a typed partial
   result, never an empty section; and
5. later pages are fresh cuts. They may add independently valid positive
   matches, but their union can never become a cross-page complete negative.
   A no-match after any continuation remains `non_atomic_search_incomplete`,
   carrying every earlier gap/skip/over-budget reason. A late-sealing operation
   may therefore appear positively on a later page without falsifying an earlier
   page-local result, but it can never be silently omitted from a global “none.”

Gate 22 introduces no database-global operation/seal high-water mark. Model
operation ordinal is Turn-local; ID, admission time, terminal time, and seal
time are not treated as clock-regression-safe monotonic frontiers. The sealed
minimal-deletion audit is different because its producer already supplies one
closed operation set and complete bundle fingerprint; only that producer-owned
closed set may support a multi-operation negative outside one live snapshot.

The SQLite cut does not freeze external file bytes or filesystem availability.
An Artifact/Representation section binds the exact already observed owner
revision and the owner reader's availability result at that read. A later
filesystem observation is a new owner cut; it cannot silently replace the
historical revision or be presented as if the database transaction snapshotted
the external source.

The Tool result represents only history committed before its Interaction cut.
Its own exact-read occurrence, Tool settlement, later Assistant presentation,
and terminal Turn do not exist early enough to be members of that result. After
those producer facts settle, the Interaction presenter may append a separately
typed `current_inspection_settlement` delta keyed to the inspection operation.
That delta is not Tool input, is not recursive self-observation, and does not
alter the pre-settlement cut. After restart it is ordinary immutable historical
Interaction evidence and may be returned by a later inspection.

### No per-record Tutor-answer causality

Context inclusion, locator delivery, a lazy read, an exact citation, temporal
order, a completed action, plausible prose, or a model's self-reported rationale
does not by itself prove that one revision governed or changed a model-authored
move.

Gate 22 never labels an individual durable record as the cause of a Tutor
answer, even when a typed owner transition or paired product trace establishes
some narrower effect elsewhere. An owner-specific command may still truthfully
say that it created, corrected, completed, or superseded its own record; that is
owner state, not reconstructed model rationale. An exact typed citation may be
shown as authored basis or provenance under the citing owner's semantics, but
it does not prove that the basis changed the authored body or objectively
entailed it.

The inspection may show the exact Context/read/citation/terminal chain so the
learner can see what is mechanically known. It must say that why the model
produced the answer is not provided by this surface. Gate 23 retains the
connected cross-Gate causal product trace as an acceptance experiment; Gate 22
does not convert that experiment into historical per-record attribution.

### Unavailable, absent, pending, and partial truth

The projection keeps these cases distinct whenever the underlying owner or
Interaction boundary distinguishes them:

- exact source or cut available;
- a trusted deletion control receipt proving full deletion at its exact root
  Session address while optional lineage is deliberately absent; that receipt
  alone does not identify a formerly descendant Session;
- an exact root Session identity retired by that control receipt, distinct from
  a never-existing Session ID or a new live Session;
- an exact administrative restore in another LearnerHome/database, valid only
  as a nonempty, completely sealed `offline_exact_restore` history at a
  different database-scoped address with no imported live `Session.revert`
  control state; it may be live before any local Turn, and the classified
  restore transition itself creates only the sealed administrative Session/
  Message/Part history named by its producer, not a Turn or operational lineage;
- an explicit same-home imported copy with fresh Interaction identities,
  completely sealed `local_import_copy` historical presentations, distinct
  from both the deleted Session and an identity-preserving restore; a separately
  admitted local root Turn may be shown only through its own Turn identity and
  strict post-frontier order, not as an inferred member of the copy manifest;
- an empty, unsafe, unsealed, partially classified, order-mismatched, or
  executable-looking imported graph, which is refused or reported as an
  integrity/unavailable state rather than current work or valid history;
- an imported Message/Part/Patch presentation, which is historical and non-
  revertible in the target Session; a later local revert may refer only to a
  post-frontier local suffix;
- bodies unavailable but the exact allowlisted whole-subtree audit retained;
- a trusted purge settlement proving that optional audit was later fully
  deleted;
- legacy source-unavailable history with no trustworthy deletion settlement;
- exact identity not found;
- exact revision absent from the inspected cut or range, together with the
  cut/section's actual complete, truncated, withheld, or unsupported coverage;
- included only as an exact locator, while aggregate omission metadata remains
  aggregate rather than record-specific;
- admitted operation with no completed action;
- pending work;
- failed or interrupted work;
- query or projection failure;
- bounded search with no match; and
- model-answer causality not provided.

No fallback transcript, cached Context copy, model summary, or derived reverse
index may silently turn deleted history back into available truth. Minimal-audit
inspection cannot expose more than exact record identity/revision,
semantic/full versus locator-only versus exactly proven not-entered Context
classification, exact read, typed citation, `completed | failed | interrupted`
operation status, deletion time, and body-deleted status. A negative
not-entered/not-read/not-cited answer is legal only after the read validates the
complete subtree operation set, closed capability/projector versions, positive
relation union, counts, ordinals, and bundle fingerprint against the surviving
seal. An indexed owner-first miss without that validation is `unknown`, not a
negative. Internal narrow-purpose operations never admitted to
`turn_model_operation` remain out of scope. Current-purpose binding, Gate 21A
action body/result, final Assistant body, model rationale, and owner-specific
finalization are outside the minimal-audit allowlist and must be labelled
unavailable there even when a corresponding live surface would expose them.

Imported history has the same no-inference boundary. A valid administrative-
history seal proves the classified transition's exact complete presentation
membership, historical-only/non-executable status, canonical order, imported-
revert exclusion, and ordering frontier. It is not an exhaustive negative
catalog over every command, domain, task-result, Event, deletion, Context, or
inspection authority, and the copy manifest alone does not establish an exact
manifest-to-root-Turn relation. A result may say what that transition created
and expressly excluded; absence from any additional authority requires that
authority's own complete query or remains unavailable. It does not prove that
the target LearnerHome observed activity at a preserved source timestamp, that
an imported Assistant or Tool ran there, or that an imported record entered
any target Context. A future source timestamp is an ordering floor for an exact
restore, not learner activity, progress, or a database-wide learning-frontier
movement. Direct shell/admin, compaction, and other non-Turn writers remain
non-Turn operations, but their Messages must appear after the imported history
under the same Session presentation frontier.

Decision ID `G22-TRUTH-001`.

### Derived inspection composition

Gate 22 takes the producer-preserving route. The closed Gate 18 lazy-read
catalog remains the sole source of `exact_read`: `course_query`,
`learning_navigation_query`, `learner_goal_query`, `learning_material_query`,
`learning_material_read`, `learning_interaction_read`,
`learner_response_evidence_read`, `future_attention_read`, `assignment_read`,
`learner_state_judgment_read`, and `advisory_plan_suggestion_read`. A new generic
inspection Tool is not added to that catalog and cannot manufacture an
`exact_read` merely by returning record-shaped metadata.

Gate 22 review found that the accepted `learning_material_query` producer did
not satisfy that rule: displayed values did not match the generic recursive
projector, flat alignment could be misclassified as its selector, disposition/
outline actions produced false no-positive results, and the pinned multi-owner
read projected only alignment. The bounded prerequisite successor keeps the
catalog unchanged but introduces action-complete material projection version 2.
It emits one trusted lineage value—possibly containing several exact records—
separate from the displayed result:

- Artifact current reads name the exact current Artifact Revision when one
  exists; exact Artifact Revision reads name the recorded Artifact plus that
  immutable Revision;
- Representation reads name the immutable Representation revision;
- Map list/get/successor reads name the immutable Map plus its current
  disposition version, and Map disposition history combines the admitted exact
  Map scope with each returned event version;
- outline-node and selector list/get reads name their exact Map-scoped node or
  selector identities;
- alignment list/get/successor reads name the globally stable alignment plus
  alignment-disposition version, take precedence over the simultaneously
  displayed selector ID, and alignment disposition history combines its
  admitted exact alignment scope with each returned event version; and
- `pinned_learning_context` emits the exact alignment, Map, selector, and every
  Artifact/Representation target revision actually returned, including a
  distinct recorded and current Artifact revision when both are present.

Every registered `learning_material_query` action is covered by the producer
matrix. Schema/action/projector parity fails closed for an unregistered future
action, so it cannot be admitted until its producer arm exists. If an
intentionally exposed action still cannot identify an exact owner record from
its output plus typed scope, it must return typed `projection_unsupported`
before operation coverage can seal; falling through to
`no_positive_relation` is illegal.

Current live lineage has no record-first index, and terminal root-Turn discovery

owner state, causal relation, or retention. Full Session deletion removes its

locator does not promote unrelated fresh-cut reverse pages into one live global
negative. Gate 22 adds no durable universal snapshot manifest or fabricated
high-water mark merely to make separately executed pages look atomic.

## Primary TUI contract

The primary natural-language TUI is the product acceptance carrier for Gate 22.
Diagnostic CLI commands, raw database queries, captured logs, direct-run, and
ACP may support evidence, but none closes the primary product-surface claim
alone.

When the ordinary Agent executes an inspection read in response to a learner
request, the TUI must expose a typed semantic result rather than hide the
completed Tool Part and rely only on model-authored paraphrase. The result may
be concise by default and expandable, but its visible summary must preserve the
decision-relevant truth:

- inspected owner and exact/current relation;
- source/author/epistemic status and uncertainty where applicable;
- owner-native potential consumer/control scope, visibly labelled as
  eligibility rather than actual use;
- the exact current-purpose binding, actual Gate 21A learner-visible action
  result, and owner finalization when those positive facts exist;
- bounded lineage coverage and exact lifecycle/availability status;
- the difference between Context presence, exact read, citation, associated
  completed operation, deleted-body audit, and unavailable/unknown lineage;
- for imported history, the exact-restore versus new-copy classification,
  complete historical-only/non-revertible status, stable presentation order,
  and boundary before every later utility or Turn without presenting source
  time as local activity;
- the fact that none of those operational relations attributes why the Tutor
  produced an answer; and
- the exact owner correction route when a correction is requested or useful.

Each section also displays or makes expandable its observation-cut identity,
fresh-versus-continuation status, query/coverage bound, and any stale/partial/
unsupported arm. The current inspection's later settlement delta is visually
separate from the pre-settlement facts it queried.

The model may explain these facts in ordinary learning language, compare
revisions, and help the learner formulate a correction. Program-owned typed
facts remain independently visible so an unsupported model paraphrase cannot
silently replace them.

The TUI must not require a full-screen dashboard or force an internal-ID menu
for ordinary cases. If several records genuinely satisfy the learner's natural
reference and choosing one would materially change the result, the Agent asks
one concise learner-level clarification. A transparent reversible local choice
remains legal where the result itself makes the scope clear.

For retained Interaction history, natural resolution begins with a keyset-paged
terminal-root directory over Turn/Session metadata only. A directory row carries
one typed thin discovery token—exact Session/Turn identity, terminal state/time,
query/cursor binding, and bounded already-retained learner-visible descriptors.
It does not construct or validate the existing Message/Part range fingerprint,
so one oversized Turn cannot hide an unbounded transcript scan inside a thin
page. The current Session is addressable directly rather than silently
excluded.

Selecting a thin token invokes a separate bounded
`materialize_interaction_locator` read. It examines at most the declared
Message/Part row and decoded-byte allowance plus one first-over-bound row. If
the full exact locator fits, the existing exact-range reader may continue from
it. If it does not, the result is `interaction_locator_over_budget`; the
directory cursor remains pinned immediately before that candidate and returns
the thin descriptor without pretending the Turn was inspected. The Agent must
not retry automatically. The learner may stop/refine, or explicitly skip that
candidate; a skip consumes a new Tool admission, advances past the exact thin
token, and permanently records `oversized_candidate_skipped` in this search's
coverage so no later page can produce a complete negative. Replaying either
Tool Part returns its original cursor/result and cannot advance, rescan, or
reset the allowance.

The cumulative search owner is the existing durable Turn model/tool budget, not
model memory or a new inspection ledger. Every successful search Tool result
persists a fixed-size authenticated continuation containing the query
fingerprint, exact last key, predecessor-cursor fingerprint, cumulative
`completeSoFar`, bounded gap/skip counts by reason, rolling gap-identity
fingerprint, and the exact Turn/Input/Tool Part that produced it. A continuation
must present that predecessor token; replay or a fresh page-one request cannot
erase prior gaps. Every directory page, locator materialization, skip, and range
page is a distinct Tool candidate in the exact inspection Turn and consumes one
tool slot; producing the next call normally also consumes another model
operation. Each call retains its own row/byte/deadline bound.

An exact Interaction range starts at offset zero unless it presents a verified
predecessor. Every ordinary later page binds its offset exactly to that
predecessor's `nextOffset`; an arbitrary or beyond-end offset cannot manufacture
an empty complete result. Deliberate forward random access requires the same
verified predecessor plus an explicit skip request and permanently increments
the authenticated range-gap count/fingerprint. Rewind, silent jump, reuse after
a predecessor declared the range complete, or omission of the predecessor is a
typed cursor conflict before reading.

“Authenticated” is database-bound, not a public self-checksum. Before reading a
continuation page, the Tool loads the exact predecessor Part and verifies its
immutable stored output bytes/fingerprint, completed candidate/invocation,
Session/Turn/Input, Tool ID, query fingerprint, cursor fingerprint, and complete
gap/skip state against the supplied token. A caller-recomputed token with erased
gaps, a surviving but wrong predecessor Part, wrong query, wrong
Session/Turn/Input, or changed result bytes returns typed
`cursor_predecessor_conflict` before any read. After
one same-Turn query result has recorded a gap, a fresh page-one request for that
same Input/query returns `cursor_reset_conflict`; only an exact predecessor
continuation or a new learner Turn may proceed. If no Part survives at the
supplied predecessor address, the caller token cannot prove whether that Part
was legally deleted, otherwise became unavailable, or never existed. The result
is `cursor_source_unavailable_or_unresolved`, performs no read, and neither
reconstructs the token nor strengthens the miss into a wrong-predecessor
conflict. `cursor_source_unavailable` requires a separately surviving authorized
producer that proves the exact predecessor existed; Gate 22 adds no Part
tombstone or deletion field for that purpose. Verifying one surviving immediate
immutable predecessor is sufficient because each stored predecessor already
commits the rolling cumulative state from its own verified parent.

The last successfully admitted search call reads the durable Turn counts/limits
after its own admission and includes both remaining model-operation and tool-
invocation capacity. If either reaches zero, that immutable Tool result
proactively returns `discovery_incomplete` with the last cursor/gap state and
`continuation_requires_new_turn`; it does not promise another same-Turn call.
Exact physical replay consumes no new count and returns those original bytes.

If a later Tool candidate reaches `tool_limit` before another Gate 22 Tool body
can run, its durable rejected candidate/envelope still supplies the exact Gate
22 Tool, Part, query/cursor input, and exhaustion receipt. The shared semantic
presenter—not the rejected Tool—may combine that typed receipt (`counter`,
observed count, limit, exact exhausted Turn) with the exact immutable
predecessor result named by the rejected cursor. A mismatch is generic Tool
exhaustion, never a guessed continuation.

`model_limit` has no rejected model operation, Tool candidate, or cursor input.
The presenter may attach a prior Gate 22 cursor only when the repository proves
one unique pending predecessor: the immediately preceding committed Gate 22
Tool result is in the same Session/Turn/Input, explicitly declares
`continuation_pending` for one query, owns the last admitted model-operation and
last settled Tool ordinal, and has no intervening learner input, model
operation, Tool candidate/result, or unrelated presentation. If that exact
predicate holds, the presenter combines the model-exhaustion receipt with that
immutable result and labels the join `predecessor_continuation_exhausted`; it
does not claim that the unrun model selected a Tool. If there is no predecessor,
more than one candidate chain, or any intervening/ambiguous work, the TUI shows
generic `model_limit` only. Prior Gate 22 cursors remain separately visible but
are not attached to the exhaustion.

The combined Tool-limit or exact-predecessor model-limit result is
`discovery_incomplete`, preserves the immutable last cursor and all cumulative
gap/skip state, and states that no new page ran. A zero-model-limit Turn with no
successful Gate 22 Part is therefore only generic Turn exhaustion: it has no
Gate 22 query identity, cursor, progress, or inspection result. Restart derives
the same fail-closed presentation from durable Turn, Part, and exhaustion truth;
it does not parse learner language, infer the unrun model's Tool choice, or
replay rejected work.

A later learner request may carry that authenticated cursor into a new Turn.
The new result identifies both the predecessor scope and its own new Turn scope,
so continuation is learner-visible rather than a reset or claim that the old
search completed. Generic exhaustion with no exact predecessor reports no Gate
22 result, cursor, or search progress. Crossing the old 64-item window is otherwise ordinary
continuation. Fully deleted history remains undiscoverable when the selected
retention mode preserves no authorized natural-reference field.

If an inspection projection is exposed through direct-run or ACP, all retained
carriers decode the same typed semantic meaning. Carrier-specific layout may
differ; owner truth, lifecycle, coverage, deletion mode, availability, causal
limitation, and settlement status may not.

## Correction and settlement

A natural learner correction follows this sequence:

1. the ordinary Agent uses bounded owner reads to resolve the intended owner-
   specific target—revision head, working selection, transition, disposition,
   alignment, claim group, or other legal relation—and exact source basis;
2. the TUI presents any consequential permission request with exact bound scope;
3. the existing owner command performs the only authorized transition;
4. shared semantic settlement reports committed, already-applied, no-effect,
   outcome-unknown, or failed truth as owned by the command; and
5. a fresh read may show the resulting owner-specific relation and preserved
   old history.

Inspection does not imply correction, and correction does not imply that the
old record was false, that it caused an earlier answer, or that the learner
accepted a suggestion. Permission rejection, stale-head conflict,
validation failure, transaction failure, or a typed failed/no-effect settlement
before any owner commit creates no replacement owner state. A later provider
failure cannot undo an already committed owner successor or its visible typed
settlement; it prevents only the uncompleted later Assistant action from being
presented as complete.

On a stale expected relation, the correction stops. The Agent performs a fresh
owner-native read, re-resolves the learner's natural target, and shows the
material change. It never automatically submits a second command merely because
the new state looks similar; a materially changed target requires fresh learner
intent or an already authorized unambiguous command scope.

Restart or reconnect reuses durable owner/Interaction/settlement truth. It does
not rerun an ambiguous model operation, replay a consequential write, rebuild
an old Context under a new renderer, or manufacture a completed action.

Decision ID `G22-CORRECT-001`.

## Reuse audit

### Reuse unchanged

Gate 22 reuses where the owner matrix marks the shape supported:

- existing owner-native current, exact-revision, history, and bounded-directory
  reads;
- existing owner correction tools, permission catalog, command settlement, and
  replay/recovery semantics;
- immutable LearningContext cuts and their exact operation/fingerprint binding;
- durable Tool Parts, Assistant content, Turn terminal state, and bounded
  Interaction reads;
- ordinary natural-language TUI request handling; and
- the shared semantic-presentation pattern already decoded by TUI, direct-run,
  and ACP for consequential learning results.

### Adapt only at the missing composition seam

Current source observation identifies five concrete composition seams:

1. ordinary owner-read Tool Parts have no shared typed inspection-result
   projection in the default TUI and may be hidden when details are collapsed;
2. live Context/lineage storage is Assistant-first and lacks an exact owner-
   revision-first index and bounded query;
3. the deletion audit has an indexed reverse lookup and a separate complete-
   seal validator, but no one bounded root/bundle-bound read that provides both;
4. administrative-history integrity is currently a whole-Session validator and
   lacks a bounded typed classification/membership/frontier projection; and
5. terminal root-Interaction discovery stops at 64 and has no continuation
   cursor.

Gate 22 adapts the existing registered owner reads, Interaction read and shared
semantic presenter at only these seams. The exact logical reads and minimum
record-first/keyset indexes are specified above; package topology remains an
implementation choice. Missing owner shapes in the closed matrix remain typed
unsupported rather than silently widening the Gate 18 exact-read catalog. Any
later decision to make one of those shapes a new exact-read capability is a
bounded Gate 18 producer-catalog revision and separate review dependency, not a
Gate 22 renderer shortcut.

### Reject

Gate 22 rejects:

- a universal consumption, purpose, selected-record, action, activity,
  adherence, mastery, causal-attribution, or audit table;
- model rationale or a second model call promoted into causal fact;
- transcript/prose parsing used as authoritative lineage;
- a shadow copy retained after full Session deletion or any minimal-audit field
  beyond the explicit allowlist;
- a Gate 22 cache that survives later deletion of the minimal audit;
- eager import of historical owner state or unrelated transcripts as inspection
  context; an explicitly imported copy remains a separately typed live Session
  and never supplies the deleted Session's old operational lineage;
- a GUI, mandatory dashboard, or separate inspection runtime;
- background-daemon observation or inference from silence; and
- Gate 23's integrated causal product trace or release claim.

Decision ID `G22-REUSE-001`.

### A. Owner and lineage truth
