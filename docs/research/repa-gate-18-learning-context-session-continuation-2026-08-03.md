## Parent problem and learning-loop boundary

The learning loop does not continue merely because durable state exists. Before
an interactive Tutor sample, the ordinary Agent must be able to observe the
bounded current learning situation that bears on its reply, distinguish exact
owned facts from navigation hints and omissions, and retrieve precise detail
without loading an entire LearnerHome or another Session transcript.

The current runtime already provides two different pieces:

- one Session's durable typed Message/Part history, including explicit resume
  and bounded compaction of an older head while retaining the original
  transcript; and
- an immutable retained-steering cut bound to each admitted interactive model
  operation by Gate 15.

Neither piece reconstructs long-term learning state. Existing Course,
navigation, Goal, Artifact, Representation, and Material Map query tools are
useful current reads, but requiring a fresh Agent to discover every owner
before its first sample makes product continuation depend on internal
coordination. Conversely, eagerly importing every record or old transcript
would erase owner boundaries, overflow small models, and turn a derived cache
or summary into false learning truth.

Gate 18 therefore owns one operation-bound observer:

> Every formally admitted released-v1 interactive model operation is bound
> atomically to one immutable, bounded, revision-exact learning-context cut.
> The cut contains a small structurally selected view, truthful coverage and
> omission metadata, exact owner locators, and the effective read-capability
> basis. Exact detail remains available through bounded owner-owned reads.

The cut supplies observation conditions. It does not decide which Tutor move
is useful, what the learner meant, which pressure governs, or whether any
domain write should occur.

Decision ID `G18-CTX-001`. Revision owner: this Gate contract until accepted;
after acceptance, the owning product/architecture documents for any challenged
meaning and this contract for Gate-local mechanics.

## Falsification of the tempting shortcuts

### Existing tool composition is not complete context

The released-v1 Session spine exposes Course, navigation, Goal, and material
metadata tools, but their mere registration does not guarantee that a fresh
sample knows which owner families exist, whether a result is complete, or which
revision a later answer used. Some cursors describe a current query rather than
a frozen historical page. A model that sees only the first bounded page can
mistake cropping for uniqueness.

Gate 18 must therefore project per-owner scope and coverage before ordinary
semantic choice. Lazy current discovery remains useful, but it is not silently
represented as expansion of the old cut.

### One shared frontier is not a universal snapshot revision

`LearningFrontier` is a causal audit coordinate for transitions that advance
it. It does not freeze trusted time, live external availability, Session
deletion, or every derived read. For example, a Goal's target-time relation can
change as trusted time advances without a learning write, and Session-tree
deletion can make an Interaction source unavailable without advancing a
learning-domain frontier.

Reading owners independently and comparing only a before/after frontier can
therefore assemble a mixed-time or mixed-source view while appearing
consistent. All database-derived automatic projection data must instead be
materialized inside the model-admission transaction, under one database
snapshot and one trusted `cutAsOf`. The shared frontier is recorded as
provenance, not promoted into a universal revision.

### “Relevant” cannot mean host-side language interpretation

The host does not parse the learner's open-language request to select a Course,
Goal, material, or previous Session. Such a resolver would duplicate the
ordinary Agent, repeat the failed universal-selector direction, and make an
uninspectable ranking look deterministic.

Automatic relevance is limited to exact structural relations:

- the learner's current default Course, if one exists;
- the exact working Course/View selection and route anchor for an included
  Course;
- bounded current owner candidate indices in canonical, explicitly
  non-priority order;
- exact material locators structurally referenced by included Course/View,
  selection, anchor, or current-Session typed records; and
- bounded recent Interaction locators, not old transcript bodies.

The current request itself remains ordinary model context. The Agent may use it
with the projected map and owner tools to make the semantic choice.

### Transcript reconstruction is not learning-state reconstruction

Resuming a Session reconstructs that Session's own conversation. Starting a
new Session must not copy another Session's Messages, Parts, compaction summary,
or assistant conclusions into the new history. A Session title or other
existing descriptive locator may be shown only as a labelled navigation hint,
never as learning truth or a substitute for an exact Interaction read.

Explicit Session fork remains the accepted exception: it deliberately clones
the source transcript with fork provenance. That is not ordinary fresh-Session
continuation, and every later interactive operation in the fork still receives
its own new Gate 18 cut.

### A bounded projection does not prove the whole request fits

A byte cap on Gate 18's block cannot prove provider token fit. The final
request also contains the product/system prompts, same-Session history,
compaction summary and retained tail, Gate 15 steering, final provider-visible
tool definitions, MCP and
skill instructions, provider transforms, and plugin extensions. Model
catalogues may report an unknown context limit, and the default AI SDK route
does not expose one universal exact tokenizer.

Gate 18 therefore owns an exact hard bound on its own stored and rendered
contribution. The existing request path must account for that contribution in
its final-envelope capacity check and report uncertainty honestly; it must not
invent a global minimum model window or claim exact token fit where the
provider supplies no exact counter.

### Current-use material resolution is not a pure read

Gate 13's current-use target resolution may observe an Artifact again, and
Representation historical/current-use reads may reconcile and persist
availability observations. Calling either path while constructing context or
serving a purportedly pure exact lazy read would make model observation mutate
learning state.

Gate 18 requires new or factored owner-private pure projections/readers for the
needed exact metadata and bytes. They may verify immutable identity, digest,
selector witness, and current physical availability, but they must not write an
observation, availability transition, frontier event, or domain receipt.
“Pure” changes side effects, not admission meaning: ordinary Tutor bytes must
still satisfy Gate 13 current-use and Gate 10 current-operation authority.
Gate 11/13 historical access remains explicit audit-only.

## Admitted operation surface

The applicability predicate is the trusted request-composition type, not Agent
name, visibility, mode, carrier, or prompt text.

Every released-v1 `composition.type === "interactive"` provider operation is
eligible, including:

- a root Turn's first sample in a fresh or resumed Session;
- later samples in the same Turn after a tool result;
- exact-target steer continuations;
- a post-compaction continuation;
- child/delegated task Sessions;
- explicit fork Sessions;
- hidden or custom named Agents that are still admitted as interactive;
- text and structured-output requests; and
- requests originating in the primary TUI, direct run, attach/local server,
  HTTP Session path, ACP, or retained task/subagent carrier when those carriers
  converge on the released-v1 Session spine.

The following are not Gate 18 consumers:

- title, compaction, and project-copy-name internal model operations;
- Gate 11's dedicated Representation producer;
- configuration-time Agent generation;
- deterministic summaries, status projections, commands, and reads with no
  model sampling;
- MCP sampling, which remains disabled in the baseline; and
- preview-v2 or any other unadmitted runtime.

Internal operations retain their narrow purpose prompts, no interactive tools,
no Gate 18 learning block, and no implied access to learning state.

Decision ID `G18-SURFACE-001`. Counterexample: an Agent named `compaction`
invoked through an interactive Turn still receives Gate 18 context, while an
ordinary Agent name used by the trusted internal-title path does not.

## The immutable context cut

### Identity and lifecycle

Exactly one Gate 18 cut belongs to one admitted Turn model operation and is
addressed by the operation's exact:

- implicit native Repa database/LearnerHome binding;
- Session ID;
- Turn ID;
- current Turn input ID and causal occurrence ID;
- Assistant Message ID;
- model-operation ordinal;
- trusted `cutAsOf`; and
- recorded shared-frontier coordinate.

The cut is created and persisted in the same native database transaction that
admits the model operation and commits its Assistant presentation. It is
Interaction-owned operation evidence, not a new learning-domain owner. A
fresh admission either commits the operation, its Gate 15 cut, and its Gate 18
cut together, or commits none of them.

The database that contains the operation is the LearnerHome identity boundary.
Gate 18 does not add a redundant learner ID to every row or render a database
path or credential to the model.

An exact retry or recovery path reads the stored structured cut and its exact
stored rendered block. It does not rerun owner queries, advance trusted time,
replace the Gate 15 cut, or render with a newer renderer. A conflicting
operation envelope or context fingerprint fails closed. Under learner-selected
full Session deletion the cut becomes source-unavailable. Under the bounded
minimal-audit correction, once its implementation/evidence is independently
accepted, the allowlisted body-free inclusion/read/citation/terminal
classification may survive; no Context body or hidden copy is replayable truth.

The context cut is immutable. Correcting an owner after admission changes a
later operation's cut and preserves the old cut as the conditions of the old
sample. There is no “update context” mutation and no attempt to make an old
model answer retroactively current.

### Canonical structure

The stored canonical value has a closed, versioned shape equivalent to:

```text
LearningContextCut {
  schemaVersion
  policyVersion
  rendererVersion
  operation {
    sessionID
    turnID
    inputID
    causalOccurrenceID
    assistantMessageID
    ordinal
  }
  cutAsOf
  throughSharedFrontier { sequence, time }
  retainedSteering {
    assistantMessageID
    cutAsOf
    fingerprint
  }
  capabilityBasis {
    catalogVersion
    policyFingerprint
    effectiveAutomaticContext
    effectiveLazyReadCapabilities[]
    effectiveProviderToolSurfaceBinding {
      route
      toolChoice { value, canonicalBytes, fingerprint }
      definitions[] {
        id
        canonicalBytes
        fingerprint
      }
      definitionCount
      combinedCanonicalBytes
      fingerprint
    }
  }
  sections[] {
    owner
    scope
    selectionBasis
    coverage
    countAtCut
    omission
    entries[]
  }
  budget {
    canonicalBytes
    renderedBytes
    entryCounts
    hardLimits
  }
  fingerprint
  renderedFingerprint
}

persisted beside the cut under the same model operation:
  exact renderedBlock bytes
```

This is a semantic shape, not a preselected table or TypeScript module layout.
Every persisted JSON boundary needs strict decoding and database constraints
appropriate to an existing-database migration. Exact field vocabulary may be
refined during implementation only if the accepted distinctions and replay
proof remain identical.

The context fingerprint covers the canonical cut. The rendered fingerprint
covers the exact UTF-8 bytes sent as the protected Gate 18 system contribution.
The model operation's request/context evidence binds both Gate 15 and Gate 18
fingerprints. Recording only owner query parameters or a renderer version is
insufficient because a later owner mutation or renderer change could produce
different bytes.

The complete provider-tool surface is canonicalized only after permission and
user filtering plus route-specific transformation. A definition includes its
ID/name, complete description, route-transformed input schema, output schema
when sent, strictness, cache/native/provider metadata and every other
semantic- or size-bearing field actually visible to that route, including a
synthetic compatibility tool. Host-only execute callbacks, credentials, and
headers are excluded. Applicable tool choice is part of the combined surface.

The full canonical definitions are **not** embedded in the Gate 18 cut or its
rendered learning-context block. The cut stores an ordered binding containing
the route, exact route-visible tool-choice value/fingerprint/canonical byte
count, each definition's ID/fingerprint/canonical byte count, definition count,
and the combined surface fingerprint and byte count. These binding bytes count
toward the 32-KiB cut; the complete definition bodies do not. One canonical
full-surface value—not a separately reconstructed approximation—is the source
for those bindings, whole-request capacity accounting, and actual dispatch on
AI SDK and native paths. An input-schema fingerprint alone is not sufficient.

Gate 18 does not claim that its durable cut can reconstruct historical tool
definition bodies. An in-process transport retry reuses the already prepared
operation envelope; crash recovery does not redispatch blindly. Any future
requirement to reconstruct and retransmit complete historical provider-tool
definitions would need a separate operation-envelope storage contract with its
own explicit resource bound rather than consuming or weakening the Gate 18 cut
bound.

### Coverage semantics

`coverage` is scoped, not global. It is one of:

- `complete` — every member of the explicitly named structural/query scope at
  the cut is represented;
- `truncated` — the scope had more eligible members than the policy admitted;
- `locator_only` — exact identity is present while semantic body fields require
  an owner read;
- `empty` — the declared scope had no member;
- `unavailable` — an exact source or stored representation cannot currently be
  supplied;
- `not_authorized` — effective automatic-context policy withheld the section;
  or
- `not_applicable` — the owner has no meaningful scope for this operation.

The cut records `countAtCut` where the owner can prove it in the admission
transaction, plus exact omitted count or an explicit `unknown` and reason.
A continuation cursor is included only when the owner proves that it continues
the same frozen scope. Existing fresh-current cursors must not be relabelled as
same-cut continuation.

Canonical ordering is stable for replay and is labelled “not priority.” A
default Course, current working selection, or route anchor is a structural
retrieval prior, not a claim that it should govern the Tutor's next move.

Decision ID `G18-CUT-001`.

For every mutable owner, “revision exact” means the owner's real tuple above,
not a generic `revision` string. For every derived field, the cut records its
`asOf` and exact dependency locators. For every unavailable locator, the cut
preserves the last exact stored identity and describes the unavailable
condition without inventing current bytes.

A projected material `current-use eligibility` value is only the owner-derived
database decision at `cutAsOf` with its complete dependency tuple. It neither
proves the backing bytes remain available nor authorizes their later
disclosure. The lazy invocation repeats admission under its current database
snapshot, current operation authority, bounded I/O result, and final
revalidation.

A Gate 17 bootstrap receipt is useful Interaction provenance and may point to
its committed children, but it is not the current Course, material, selection,
or anchor authority. Gate 18 reconstructs those facts from their owning
records and exact revisions; it does not replay the composite receipt as a
long-term context snapshot.

Automatic projection performs database reads only. It does not inspect the live
filesystem, invoke conversion, fetch remote content, search embeddings, or
enumerate or observe content through a ContentRoot. It may bind the exact
stored ContentRoot/grant/workspace/one-operation receipt already referenced by
a material locator, but that receipt is provenance only. It is neither current
invocation authority nor evidence that a path still contains the recorded
bytes. A durable ContentRoot locator may support a fresh current-operation
authorization after current binding/grant/capability checks. Active-workspace
and one-operation receipts grant no cross-Session discovery or reuse.

Decision ID `G18-PRODUCER-001`.

## Automatic working-view policy

The policy gives the ordinary Agent a map without preselecting its move:

1. Always emit the operation/cut header, Gate 15 reference, policy/capability
   basis, and one coverage record for each current producer family.
2. Include the exact default-Course transition if one exists. For that Course,
   include its exact current working selection and exact current route anchor
   if present.
3. Include up to eight eligible Course candidates and up to eight eligible Goal
   candidates in owner-defined canonical order. The order is not a priority
   score. Counts and omissions are explicit.
4. Include up to eight exact Artifact/Representation/Map/alignment locator
   groups reached through the included structural records. Do not choose a
   global latest or preferred material.
5. Include up to four recent addressable terminal root-Turn locators from other
   Sessions in reverse chronological order. Preserve a source-unavailable
   locator when the Interaction owner retains one; do not pretend to count
   physically deleted records that leave no addressable tombstone. An existing
   Session title may appear only as a complete, labelled, untrusted navigation
   hint.
6. Prefer at least one minimal locator/coverage record for every applicable,
   authorized producer family before spending remaining bytes on extra entries.
   A crowded Course list must not silently starve Goal, Interaction, or material
   coverage.
7. Include only whole typed fields. A field or body that exceeds its entry
   allowance becomes locator-only with exact byte count/digest and an omission
   reason; semantic strings are not cut mid-value and presented as complete.

This policy is deterministic over the same transaction snapshot, trusted time,
capability basis, and policy version. It contains no keyword matching,
embedding similarity, model call, task classifier, curriculum score, priority
scalar, or exhaustive candidate proof.

The eight/four limits are resource policy, not product truth. They may change
through an explicit policy/contract revision with comparative omission and
cost evidence; changing them cannot rewrite an old cut.

Decision ID `G18-VIEW-001`.

## Lazy owner reads

### Read purposes must remain visibly distinct

1. **Pinned metadata expansion** consumes an exact locator from a Gate 18 cut.
   It returns that exact stored owner revision/range or a typed
   unavailable/stale result. It never retargets to a new head, latest
   Representation, same path's new Artifact Revision, replacement selector, or
   newer Session range. A locator or metadata result alone grants no byte-read
   authority.
2. **Tutor current-use disclosure** may return material bytes only after the
   owning Artifact/Representation/Map and current local-read authorities admit
   those exact bytes for ordinary Tutor use at the lazy invocation. It may use
   a pinned locator as the requested identity, but it does not inherit the old
   cut's authorization or bypass later correction, withdrawal, drift, Map
   disposition, or continued-use requirements.
3. **Fresh-current query** asks an owner for its state at the later tool
   operation's trusted time. Existing Course, navigation, Goal, and material
   query capabilities may continue to serve this role. Their result is a new
   ToolPart in the current Session and may differ from the earlier cut.
4. **Historical audit disclosure**, where already accepted, remains behind its
   distinct explicit audit/inspection capability. It is never wired to the
   ordinary Tutor context capability or exposed as a `historical=true` option
   on a common current-use reader.

Tool names and module placement are implementation details, but the capability
boundary is owner-specific. Gate 18 does not introduce one universal context
gateway, generic CRUD reader, or cross-owner repository.

### Required pure-read shapes

- Course/View expansion accepts exact Course/View/Revision/item identities and
  returns exact stored state, mapping, or a typed missing/superseded result.
- Navigation expansion accepts the exact default/anchor transition identity;
  a fresh-current navigation query remains separate.
- Goal expansion accepts an exact Goal Revision and returns that immutable
  revision/history page with source and lifecycle provenance. Time relation is
  either the cut-stored value or a new value explicitly labelled with the
  later query time.
- Artifact/Representation/Map metadata expansion accepts the full exact
  identity tuple and returns no bytes. The ordinary Tutor byte reader is a new
  zero-write owner boundary that preserves Gate 13 current-use admission:
  it requires the exact active Map/disposition and selector witness where a Map
  locator is used; the current Artifact ordinary-use snapshot
  (`effectiveArtifactID`, disposition version, current Revision,
  fingerprint/media type, attribution, and lineage version); the exact
  Representation Revision/source Revision/accepted lineage/attribution,
  availability version and disposition; and, after source drift, the exact
  active continued-use grant identity, version, disposition, old/current
  Revision pair, current lineage, and current attribution dependencies.
  Creation-time `sourceProof` is provenance and does not replace these
  current-use dependencies.
- The zero-write Tutor reader performs owner admission in a database snapshot,
  verifies the exact object/digest or active raw source under bounded I/O, then
  revalidates the complete admission tuple before returning content. It
  suppresses only observation/availability persistence; it does not weaken
  current-use eligibility. Missing, drifted, revoked, withdrawn, inactive-Map,
  selector-mismatch, availability-changed, or grant-stale cases return typed
  no-content outcomes. It never calls `HistoricalReader` for an ordinary Tutor
  request.
- An old raw Artifact Revision is disclosed to the Tutor only when the active
  source still resolves to those exact bytes or a separately accepted retained
  backing exists. Gate 18 creates no retained backing and never substitutes new
  bytes found at an old path. Historical Representation/selector bytes remain
  audit-only under their distinct capability.
- Every local byte-read invocation obtains fresh effective Gate 10 authority;
  a stored authorization snapshot is never a token. A durable ContentRoot
  locator must resolve its current exact binding and active observation grant
  under the current capability/policy. An active-workspace provenance locator
  is usable only when the current invocation independently has the same exact
  workspace/profile authority. A stored one-operation receipt is provenance
  only: the current invocation needs a newly issued exact operation-scoped
  learner approval, otherwise it returns `not_authorized`/unavailable. The
  three arms never union, and only ContentRoot supplies cross-Session
  discovery identity.
- Interaction expansion lists bounded root-Turn locators or reads one exact
  Message/Part range by Session/Turn/message identity. It never falls back to a
  similarly titled Session, a latest Turn, or a hidden transcript copy.

Each physical lazy invocation is bounded to at most 32,768 UTF-8 output bytes
and 64 typed items, with lower owner/caller limits allowed. Larger content uses
exact ranges or pages with source identity, coordinate, digest where
applicable, returned count, and truthful remainder. Generic transport
truncation is not an owner proof and must not silently turn a partial record
into a complete one.

A pinned metadata expansion that observes later owner correction reports the
requested old metadata revision if it remains stored, or its typed
unavailable/superseded state. Tutor byte disclosure additionally requires
current-use and current-invocation authority above; integrity-valid historical
bytes alone are insufficient. No path “helpfully” substitutes a corrected
revision. The Agent can issue a separate fresh-current query and the next model
operation will receive a new cut.

Lazy reads may write their normal ToolPart and Turn invocation evidence in the
current Interaction. They perform zero learning-domain writes and do not
advance the shared learning frontier.

Decision ID `G18-LAZY-001`.

## Gate 15 steering reuse

Gate 18 consumes Gate 15's exact cut as an opaque, already owned operation
input:

- both cuts share the same Assistant Message ID and admission transaction;
- Gate 18 records Gate 15's exact fingerprint and `cutAsOf`;
- Gate 15's own protected rendered block remains independently rendered by its
  owner;
- Gate 18 neither copies steering instructions into its sections nor selects,
  ranks, summarizes, expires, broadens, or repairs them; and
- a mismatch between the two operation identities, times, frontiers, or
  fingerprints aborts admission.

The learning-context block must be protected from plugin removal or
deduplication to the same degree as the product prompt and Gate 15 block.
Plugins may extend ordinary interactive prompts, but they cannot replace the
stored Gate 18 bytes or make an internal operation interactive.

Decision ID `G18-STEER-001`. This is a consuming contract only; it does not
revise `G15-POL-001` or Gate 15's steering cut.

## Capability and permission boundary

Every interactive operation receives a Gate 18 cut header. Automatic domain
sections are populated only under one registered read-only automatic-context
capability and the exact configured/delegated policy intersection. A restricted
or delegated Agent that lacks that capability receives explicit
`not_authorized` coverage and no hidden domain data.

The persisted cut still binds the operation to its owning database implicitly,
but an unauthorized model-visible header contains only the context
schema/policy, operation-local binding, and withholding state. It does not
render a database path, opaque cross-Session owner identity, Course/Goal count,
or other domain locator.

Pinned/fresh lazy reads additionally require their owner-specific registered
read capabilities. The cut records which exact read capabilities were
effective and binds the final provider-visible tool surface for the sample. A
locator whose reader is not effective is labelled unavailable to this
operation; the prompt does not imply that the model can fetch it. Material
bytes additionally require fresh current-operation Gate 10 authority and Gate
13 current-use admission; read-capability visibility does not satisfy either.

The automatic-context capability:

- is present in the authoritative capability/permission catalogue;
- is allowed for the ordinary default Tutor policy;
- is default-denied for restricted custom Agents unless explicitly allowed;
- intersects rather than replaces delegated capability;
- grants no write, root, shell, network, conversion, or observation authority;
  and
- does not make a model assertion, Session title, or projection-derived
  relation true.

The operation envelope uses the complete canonical final provider-visible
definition for every effective tool and the applicable tool choice, not merely
pre-permission registry names, IDs, or input-schema fingerprints. Description,
route-transformed schemas, output schema, strictness, cache/native/provider
metadata, and synthetic compatibility state are included when sent. The Gate
18 cut binds that full surface through exact per-definition/tool-choice and
combined fingerprints plus canonical byte counts without copying its bodies.
A description-only or route-only change therefore conflicts on replay and
changes capacity accounting rather than preserving the old request hash.

Decision ID `G18-CAP-001`.

## Size, capacity, overflow, and compaction

### Exact Gate 18 bounds

If this contract is accepted, its first context policy fixes these hard
ceilings:

- stored canonical structured payload, excluding the separately stored rendered
  block: at most 32,768 UTF-8 bytes;
- rendered model-facing Gate 18 block: at most 16,384 UTF-8 bytes;
- one automatic semantic entry body: at most 2,048 UTF-8 bytes;
- automatic candidates: at most eight per producer family, except at most four
  recent Interaction locators; and
- one lazy owner-read result: at most 32,768 UTF-8 bytes and 64 typed items.

Byte counts use canonical UTF-8 bytes, not JavaScript string length and not a
token estimate. The stored cut records limits and actual counts. These limits
do not include Gate 15's separately bounded protected block or the complete
provider-tool definition/tool-choice bodies. The compact tool-surface binding
stored in the cut is included in `canonicalBytes`; its
`combinedCanonicalBytes` records the separately accounted complete surface.

Deterministic budgeting proceeds from mandatory header/coverage and one minimal
locator per applicable authorized family, then structural default/selection/
anchor records, then extra canonical candidates. Over-limit semantic values
become locator-only; they are not substring-truncated into apparently complete
facts. If mandatory identity, coverage, and omission truth cannot fit, model
admission fails before any provider request.

### Whole-request capacity

After plugin system/parameter hooks, effective tool filtering, provider message
transformation, and effective output-reserve selection have fixed every
size-bearing semantic input available to the host, the runtime classifies the
request:

- `capacity_known` — the selected model reports a usable input/context limit;
  a conservative final-envelope check includes system blocks, messages, the
  exact canonical provider-visible tool definitions/tool choice, Gate 15,
  Gate 18, and output reserve. A known over-limit request is not transported.
- `capacity_unknown` — a zero/missing model context limit is treated as
  unknown, not unlimited and not zero capacity. Gate 18 remains hard-bounded,
  the uncertainty is recorded, and any provider overflow is surfaced
  truthfully.
- `capacity_invalid` — contradictory/negative limits or an impossible fixed
  envelope fail before transport.

Where a provider route exposes an exact tokenizer or exact serialized request
size, the runtime may use it and record the method. Otherwise the existing
estimate is explicitly conservative/approximate; passing it is not claimed as
proof that the provider will accept the request. There is no fabricated global
`MIN_CONTEXT_WINDOW` and Gate 18 does not ban custom models solely because
their limit metadata is unknown.

A post-admission capacity failure preserves the immutable cut as operation
evidence, settles the attempt truthfully without transport, and never shrinks
or resamples that cut in place. If same-Session history is compactable, the
program may run the narrow internal compaction operation and admit a distinct
interactive operation with a new Assistant Message ID and a new Gate 15/Gate 18
cut. Fixed prompts, provider-visible tool definitions, Gate 15, and Gate 18
that exceed capacity cannot be repaired by repeatedly compacting history; the
failure is terminal until configuration/model/capability/context policy
changes.

Provider context overflow is non-retryable under the same envelope. An
automatic retry may reuse the exact stored cut only for transport failures that
the retained retry contract already permits; it cannot rebuild context.

Decision ID `G18-BUDGET-001`.

## Implementation ownership and dependency direction

Gate 18 belongs at the existing released-v1 Session/Turn model-admission and
request-composition seam. The top-level application layer may coordinate one
transaction and deterministic renderer. Each learning owner supplies narrow,
transaction-scoped, pure projection functions and exact lazy readers that
preserve its own identity, revision, correction, and availability semantics.

The accepted implementation must:

- persist the structured cut and exact rendered block with the admitted model
  operation in Repa's existing native database;
- use a versioned migration and a frozen historical fixture for every
  constraint/schema change;
- share owner invariants with existing query/command paths rather than issue
  raw cross-owner SQL from the context compiler;
- factor owner-private zero-write material/Representation admission and
  revalidation that shares Gate 13 current-use predicates while suppressing
  observation/availability writes; never substitute `HistoricalReader` for
  ordinary Tutor content;
- derive canonical final provider-visible tool definitions and capabilities
  from the same authoritative catalogue, permission intersection, route
  transformation, and tool-choice path used by dispatch; derive the compact
  persisted binding and whole-request count from that same full value without
  embedding definition bodies in the Gate 18 cut;
- inject one protected deterministic block through both default AI SDK and
  retained native-adapter routes; and
- preserve current generic Session, provider, tool, permission, MCP,
  cancellation, retry, compaction, fork, child, attach, ACP, and recovery
  mechanics.

It may add an Interaction-owned context-cut schema/table or columns associated
with a model operation; that is not a second context database. It must not add
a generic manager/service/repository/controller layer, background daemon,
vector store, RAG index, soft-memory cache, alternate model loop, or preview-v2
runtime.

Exact table/column names, TypeScript module layout, prompt heading, tool
spelling, and test-file count are implementation details. The operation
identity, same-transaction cut, owner tuples, protected byte-exact rendering,
permission basis, pure reads, bounds, and failure semantics are contract
requirements.

- eager Course detail, whole material, whole LearnerHome, or cross-Session

### Schema, identity, and transactional evidence

- one fresh model-admission transaction commits the model operation,

### Producer and pure-read evidence

For every producer row in the matrix:

- fixtures cover absent, one, many, corrected/superseded, withdrawn/unavailable,

Material evidence separately covers pinned metadata, explicit historical audit,

Revisions, retained-backing absence, current Artifact ordinary-use snapshots,

ContentRoot succeeds across restart only after fresh current binding/grant and

workspace/child. A stored one-operation receipt fails across operations,
restart, fresh Session, and child until a new exact approval is issued. No old
authorization snapshot is accepted as a token and the arms never union.

Interaction evidence covers recent root-Turn enumeration, exact bounded
Message/Part range, deleted source, duplicate Session title, same title with
different Turn identity, fork provenance, compaction replay provenance, and no
fallback to latest/similar transcript.

### Applicability, capability, and carrier evidence

- a single trusted composition predicate covers fresh/resumed root, tool
  continuation, steer, post-compaction, child, fork, hidden/custom Agent, and
  structured-output operations;
- title, compaction, project-copy-name, Representation generation,
  Agent-generation, deterministic paths, disabled MCP sampling, and preview-v2

- default, restricted, and delegated Agents show exact automatic-context and
  lazy-read capability intersections; omitted/new capabilities do not inherit

- canonical effective provider-tool definitions and tool choice match what the
  route actually receives after permission/user filtering and route

- a permitted MCP/custom definition larger than 32,768 UTF-8 bytes with a

  and a one-byte description or schema change changes the per-definition and
  combined fingerprints;
- TUI, direct run, attach/local server, HTTP Session, ACP, and child/task
  carriers that reach the interactive spine produce the same semantic cut for
  the same database snapshot and trusted inputs; and
- default AI SDK and retained native-adapter routes receive byte-identical

### Session, budget, and failure evidence

- an ordinary fresh Session receives current long-term state and recent
  Interaction locators but no old Message/Part body or compaction summary;
- a resumed Session retains its own transcript and receives newly corrected

- an explicit fork is distinguished from fresh continuation and a child gets

- a domain write, fresh-current query, learner correction, or steer followed by

- canonical/rendered/entry/lazy bounds are checked in UTF-8 bytes with boundary

- known, unknown, invalid, and plugin-expanded model envelopes exercise honest

- a compactable history performs one narrow internal compaction and then a new

- fault injection covers owner projection, operation/cut commit, provider

Real released-v1 traces use the ordinary production Agent, not a special parser
or selector benchmark, and compare stored context bytes with the actual

- a fresh LearnerHome, one Course, and several Courses/Goals where the named

## Grill disposition and independent-review handoff

The design/evidence grill found no unresolved maintainer-owned choice that must
precede contract review:

- structural non-starving coverage avoids choosing a host-side relevance or
  priority policy;
- preserving unknown-capacity model support with explicit uncertainty avoids
  turning Gate 18 into an unrelated provider-eligibility Gate;
- exact numerical limits are versioned, reversible engineering resource policy
  and are fixed above for falsifiable review;
- existing accepted Session fork/child/compaction semantics decide the
  fresh/resumed distinctions; and
- Gate 15 already owns the steering cut, so Gate 18 has no authority to choose
  a competing composition.

The semantic spine was complete enough to enter fresh, separate, top-level
contract/theory review. Initial review and closure should try to reject this
draft on the following exact questions:

1. Does the same-transaction cut really prevent mixed owner/time/Session state,
   or is a producer still read outside the admission snapshot?
2. Does any claimed exact locator omit an owner version, mutable disposition,
   attribution, availability, source, or cross-owner dependency needed to stop
   retargeting?
3. Can automatic structural coverage still encode a hidden Tutor-move
   selection, fabricate uniqueness through truncation, or starve a producer?
4. Can any context or lazy-read path mutate Artifact/Representation
   observation state, advance the frontier, or substitute current for exact
   historical data?
5. Are ordinary fresh, resumed, child, explicit fork, tool continuation, steer,
   and post-compaction paths distinguished without copying another transcript?
